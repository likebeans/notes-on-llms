# 关于本站

Notes on LLMs 是一份面向中文读者的大模型学习手册。它更像“持续整理的研究/工程笔记”，而不是一次写完的教材。

## 适合谁

- 想从 Prompt、RAG、Agent 开始做 LLM 应用的开发者。
- 想补训练、微调、对齐、评估和多模态基础的算法工程师。
- 正在准备 LLM 应用/算法/平台方向面试的人。
- 已经做过一些 AI demo，但想把它们推向更可靠系统的人。

## 作者视角

本站采用“工程可落地优先”的组织方式：先解释问题和失败模式，再补论文、架构和实现细节。对于快速变化的模型/API，页面会尽量标出技术版本和内容状态。

## 内容状态

| 状态 | 含义 |
| --- | --- |
| `verified` | 已按当前资料复核，适合作为主线引用 |
| `needs-review` | 已整理但仍需继续校验，阅读时注意技术版本 |
| `opinion` | 包含作者经验判断，不等同于标准答案 |
| `historical` | 保留历史背景或旧方案，不代表当前推荐实践 |
| `draft` | 草稿，不进入公开主线 |

## 来源政策

- 概念定义优先参考论文、官方文档、官方博客和项目仓库。
- 工程建议会结合真实项目经验，但应配合评估样本验证。
- 涉及 API、模型版本、价格和发布状态的内容容易过期，需要按日期复核。
- 不确定的信息会保持 `needs-review`，避免把“看起来合理”写成事实。

## 更新流程

1. 先补齐 frontmatter：标题、模块、状态、更新时间和技术版本。
2. 再整理正文：目标、核心概念、实践步骤、常见失败。
3. 对关键资源补官方链接或原始论文。
4. 运行内容检查和站点构建。
5. 重要页面进入后续复核队列。

## 如何阅读一篇技术文章

主线文章按问题、原理、取舍、实践与验证组织。公式需要说明符号与适用条件，代码需要说明依赖与是否完整，效果数字需要说明样本和评估口径。没有测量依据的数值应视为教学设定，而不是性能承诺。

- `updated` 表示站内内容发生编辑，不等于所有技术结论已重新核验。
- `reviewed` 结合技术版本与正文说明理解，不能推导所有硬件和 SDK 组合都已测试。
- `verified` 也有版本与范围；超出原文条件时仍需验证。
- 镜像的原始发布时间与站内整理时间分开保留，新增导读不改变原文观点归属。

工程建议是待验证的方案。只有提供了数据、配置与结果，才把某项改动写成已经获得的收益。


## 复核范围与学习记录

页面的“资料复核”日期与“代码验证”分开记录。`reviewScope` 说明本轮对照的资料或实验，`exampleStatus` 区分本轮未实跑、部分示例运行和配套示例运行；没有登记的页面不会自动显示为已测试。外部资料链接按正文中可点击的 HTTP(S) 链接去重统计，代码示例和独立图片地址不计入，该数量不代表来源质量。

[技术核验索引](/resources/updates) 提供本轮更新入口。[文章检索与学习记录](/guide/library) 可以筛选文章、查看收藏和继续阅读；已读和收藏仅保存在当前浏览器，不跨设备同步，也不会发送到服务器。清除浏览器站点数据会移除记录。章节位置与手动标记的完成数量分别显示，不把打开最后一章当作完成全部学习。
