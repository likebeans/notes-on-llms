# Notes on LLMs 知识站重构设计

- 状态：已完成方案讨论，等待书面规格确认
- 日期：2026-08-24
- 项目：https://github.com/likebeans/notes-on-llms
- 线上站点：https://likebeans.github.io/notes-on-llms/

## 1. 背景

Notes on LLMs 已经积累了覆盖 RAG、Agent、MCP、Prompt、训练和多模态等方向的系统性内容，但目前更接近默认文档站，而不是具有清晰作者身份、学习路径和内容可信度的技术知识品牌。

现状审查发现以下主要问题：

- 部分 HTML 链接直接使用根路径，未考虑 GitHub Pages 的 `/notes-on-llms/` base，导致线上 404。
- 首页更新信息需要手工维护，线上仍显示较早的更新时间。
- 导航层级与长文章目录较密集，读者不容易判断从哪里开始以及下一步学习什么。
- 部分高曝光入口为空白页或占位页，降低站点完成度。
- 文章缺少统一的难度、前置知识、核验日期、适用版本和内容状态。
- SEO 元数据不完整，favicon、canonical、社交分享元数据和结构化数据需要补齐。
- 主题样式集中在大型自定义 CSS 中，后续维护和页面复用成本较高。
- 部分技术内容存在过时风险，需要依据官方文档、原始论文和当前实践重新核验。

本次重构属于架构级升级，但继续沿用现有静态站技术栈，避免引入不必要的运行时系统。

## 2. 目标

### 2.1 产品目标

将站点升级为“研究手册 + 知识地图”形态，让读者可以：

1. 快速理解站点覆盖的知识范围。
2. 根据自己的目标选择清晰的学习路径。
3. 在阅读文章前判断难度、前置知识、时效和可信度。
4. 在阅读后自然进入下一篇相关内容。
5. 清楚区分已核验事实、作者经验、历史内容和待复核内容。

### 2.2 技术目标

- 保持 VitePress、Vue 3、Markdown、GitHub Pages 的静态架构。
- 修复所有 GitHub Pages base 路径问题和失效站内链接。
- 通过统一内容模型驱动首页、导航、最近更新、文章元信息和搜索可见性。
- 将视觉元素拆分为职责明确、可单独维护的 Vue 组件。
- 在构建阶段拦截失效链接、缺失元数据和不应发布的草稿。
- 补齐基础 SEO、社交分享和文章结构化数据。

### 2.3 首期成功标准

- 首页、学习路径、全部导航入口和六个技术模块概览页完成重写或补全。
- 所有公开入口均有有效内容，不再展示空白页或明显占位页。
- 站内链接在本地根路径和 GitHub Pages `/notes-on-llms/` base 下均可用。
- 正式文章能够展示统一元信息、内容状态和下一步学习入口。
- 首页最近更新由内容数据自动生成。
- 桌面、平板和手机布局无横向溢出，导航、搜索、代码块和 Mermaid 图表可用。
- 生产构建、内容检查和链接检查通过，浏览器控制台无新增错误。
- Lighthouse 的 Performance、Accessibility 和 SEO 三项在生产预览中均达到 90 分以上；如果第三方字体或 Mermaid 渲染造成波动，以连续两次检测的较低结果为准。

## 3. 非目标

首期不建设以下功能：

- 登录、用户账户、评论、收藏和学习进度云同步。
- 数据库、运行时 API、无头 CMS 或服务端全文搜索。
- 自动将 AI 生成内容直接发布到生产环境。
- 对全部深层技术文章一次性改写。
- 与本次知识站体验无关的基础设施重构。

## 4. 设计方向

采用已确认的 A 方向：“研究手册 + 知识地图”。整体视觉应同时表达作者感、研究气质和系统性，而不是继续模仿通用产品文档。

### 4.1 视觉语言

- 背景使用温暖的纸张色，正文使用深墨色，降低长时间阅读疲劳。
- 钴蓝色作为导航、链接和学习进度的主要强调色。
- 绿色用于“已核验”等可信度状态，橙色用于实践提示和需要注意的信息。
- 大标题使用编辑感较强的衬线字体；正文使用高可读无衬线字体；编号与技术标签使用等宽字体。
- 使用细网格、细分隔线、章节编号和轻量卡片建立“研究手册”感，避免大面积渐变、玻璃拟态和过度圆角。
- 深色模式保留相同的语义色关系，不简单反转颜色。

### 4.2 首页

首页从上至下包含：

1. 品牌导航：Notes on LLMs、学习路径、知识体系、实践和搜索。
2. 核心主张：说明站点帮助读者从模型原理走到可运行的智能系统。
3. 两个主要行动：选择学习路径、打开知识地图。
4. 知识地图：展示六个核心模块及其关系。
5. 学习路径：至少提供应用开发、算法工程和面试冲刺三个入口。
6. 最近更新：从文章元数据自动读取，不在首页手工复制日期和摘要。
7. 作者与站点说明：解释内容定位、核验方法和仓库入口。

首页在手机端改为单列，知识地图保持可读的纵向关系，不缩放成无法点击的桌面图。

### 4.3 文章页

桌面文章页采用三栏结构：

- 左栏：所属模块、模块学习进度和同模块文章顺序。
- 中栏：文章正文、元信息、学习目标、图表、内容状态、来源和下一篇。
- 右栏：当前文章目录、阅读进度和 GitHub 编辑入口。

平板隐藏右侧目录，手机同时收起左右栏，在顶部提供目录入口和阅读进度。正文保持单列，代码块和宽表格允许局部横向滚动，但页面本身不得横向溢出。

文章开头依次展示：所属模块、内容状态、标题、摘要、难度、预计阅读时间、前置知识、适用版本和“本篇你会学到”。文章末尾依次展示：内容核验信息、参考资料、相关文章和下一篇学习建议。

## 5. 信息架构

顶层导航稳定为：

- 学习路径
- 知识体系
- 实践
- 关于

“知识体系”下组织六个一级模块：

1. RAG
2. Agent
3. MCP
4. Prompt
5. Training
6. Multimodal

每个模块包含一个概览页，概览页说明学习目标、前置知识、推荐顺序、核心文章和当前内容状态。面试、资源和参考资料作为辅助入口保留，但只有在存在有效内容时才进入主导航；未完成页面不得以正式入口展示。

学习路径不复制文章，而是以有序列表引用现有文章。首期提供：

- 应用开发者路径：以 Prompt、RAG、Agent、MCP 和生产实践为主。
- 算法工程师路径：以模型基础、训练、对齐、多模态和评估为主。
- 面试冲刺路径：以高频概念、系统设计和实践问答为主。

## 6. 内容模型

公开页面使用统一 Frontmatter，并通过 `pageType` 区分技术文章、学习路径和站点入口。字段定义如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 页面标题 |
| `description` | 是 | 搜索结果和社交分享摘要 |
| `pageType` | 是 | `article`、`path` 或 `landing` |
| `module` | 技术文章必填 | 六个核心模块之一；非技术入口使用 `site` |
| `level` | 技术文章必填 | `beginner`、`intermediate` 或 `advanced` |
| `prerequisites` | 技术文章必填 | 前置文章路径数组；无前置知识时使用空数组 |
| `updated` | 是 | 内容最后修改日期，ISO `YYYY-MM-DD` |
| `reviewed` | 非草稿技术文章必填 | 最后人工审查日期，ISO `YYYY-MM-DD`；即使审查结论是需要更新，也记录本次审查日期 |
| `contentStatus` | 是 | `verified`、`needs-review`、`opinion`、`historical` 或 `draft` |
| `techVersion` | 技术文章必填 | 适用的模型、框架版本或时间范围 |
| `tags` | 是 | 用于聚合与搜索的标签数组 |
| `author` | 否 | 缺省时继承站点作者 `likebeans` |
| `order` | 否 | 模块内学习顺序；只在参与有序路径时填写 |

预计阅读时间只为技术文章和学习路径计算，根据正文文本在构建时生成，不要求作者手工维护。参考资料继续保存在正文的“参考资料”章节中，以便读者直接查看；构建器同时统计来源数量供文章状态组件展示。`landing` 页面只校验通用字段，不强制填写难度、前置知识或技术版本。

内容状态的展示规则：

- `verified`：显示“已核验”和核验日期。
- `needs-review`：显示“需要更新”，并提示读者谨慎采用时效性结论。
- `opinion`：显示“经验观点”，明确其不是通用事实。
- `historical`：显示“历史内容”，说明仅用于理解技术演进。
- `draft`：不进入导航、搜索、首页更新和站点地图；开发预览中直接访问时显示草稿提示，生产构建不输出草稿页面。

## 7. 内容治理流程

内容更新由当前 Markdown 作为唯一事实来源，ChatGPT 用于提出改写稿、结构优化和事实核验辅助，不直接批量覆盖并发布。

每篇文章按以下流程处理：

1. **盘点**：识别文章目标、现有观点、代码示例、外部链接和时效性陈述。
2. **分类**：将文章标记为保留、更新、重写、历史内容或草稿。
3. **重构**：补充摘要、学习目标、章节结构、元信息和下一步学习建议。
4. **核验**：时效性事实优先依据官方文档、标准、原始论文或项目仓库；搜索结果和二手文章只用于发现来源。
5. **保留作者声音**：保留个人经验、案例和有辨识度的判断；将经验观点与可验证事实分开表达。
6. **差异审查**：逐篇检查 Markdown diff、代码块、链接和图表，不接受无审查的全站自动改写。
7. **发布标记**：只有达到对应核验要求后，才设置为 `verified`。

无法可靠确认的陈述不会被补写成确定事实，而是删除、弱化表达或标记为需要复核。

### 7.1 更新批次

首期内容范围：

- 首页
- 学习路径
- 六个技术模块概览页
- 全部可见导航入口页，包括关于、资源、参考和面试入口的补全或隐藏决策

尚未进入深度改写批次的现有公开文章，也必须在首期完成最小盘点：补齐通用元数据、记录人工审查日期，并根据结果标记为 `needs-review`、`opinion`、`historical` 或 `verified`。这一步只建立可信的发布状态，不在首期重写其正文。

深层文章按以下顺序进入后续批次：

1. RAG
2. Agent
3. MCP
4. Prompt
5. Training
6. Multimodal

每个批次独立完成核验、构建和审查后再进入下一批，不将未完成的深层改写混入首期发布。

## 8. 技术架构

### 8.1 总体架构

继续使用 VitePress 1.x、Vue 3、Markdown 和现有 GitHub Pages 工作流。站点不新增运行时后端，所有派生数据在构建时生成。

数据流为：

```text
Markdown + Frontmatter
        ↓
内容校验与内容索引
        ↓
首页 / 知识地图 / 学习路径 / 最近更新 / 文章元信息
        ↓
VitePress 静态构建
        ↓
GitHub Pages /notes-on-llms/
```

### 8.2 配置边界

将当前集中配置拆分为职责明确的模块：

- 站点基础信息与 `base`
- 顶部导航
- 模块侧边栏
- SEO 与 head 元数据
- 内容状态和模块枚举
- 主题入口和组件注册

导航只维护路径和显示规则，不重复维护文章描述、更新时间等内容数据。文章数据由 Frontmatter 和构建时内容索引提供。

### 8.3 主题组件

首期建立以下复用组件：

- `HomeKnowledgeMap`：首页六模块知识地图。
- `LearningPaths`：展示学习路径及其文章序列。
- `RecentUpdates`：读取内容索引并展示最近更新。
- `ArticleMeta`：难度、阅读时间、前置知识和适用版本。
- `LearningObjectives`：文章开头的学习目标。
- `ContentStatus`：核验状态、核验日期和来源数量。
- `SourceList`：统一参考资料表现。
- `NextStep`：相关文章和下一篇学习建议。

组件只接收规范化数据，不自行扫描 Markdown 或维护第二份内容列表。构建时内容加载器负责把 Frontmatter 转换为组件需要的数据结构。

### 8.4 路径策略

- 保留 GitHub Pages `base: '/notes-on-llms/'`。
- Markdown 内部链接使用 VitePress 可解析的相对路径。
- Vue 组件生成的链接统一通过 VitePress Router 或 `withBase()`。
- 移除原始 HTML 中以 `/` 开头且绕过 base 的站内 `href`。
- 外部链接保持完整 URL，并在内容检查中报告失效或重定向异常，但外部网络波动不直接阻止构建。

## 9. SEO 与分享

站点级补充：

- 有效 favicon 和主题色。
- GitHub Pages 主站地址和 sitemap hostname。
- 默认 Open Graph 与 Twitter Card 元数据。
- 正确使用 `property` 的 Open Graph 标签。

页面级补充：

- 基于当前路径生成 canonical URL。
- 使用文章标题与 `description` 生成分享元数据。
- 正式文章生成 Article JSON-LD，包括作者、更新时间和核验时间。
- `draft` 页面不生成 sitemap 项和可索引元数据。

首期使用一张站点默认分享图；为每篇文章自动生成独立图片不在本次范围内。

## 10. 错误处理与降级

- Frontmatter 缺少必填字段：内容检查失败，并显示具体文件和字段名。
- 枚举值或日期格式无效：内容检查失败，不使用隐式默认值掩盖问题。
- 正式文章引用不存在的内部页面：生产构建失败。
- 可选字段缺失：使用站点作者等已定义的全局默认值。
- 内容状态未知：校验失败；开发预览不得将其当作“已核验”。
- 最近更新没有合格文章：显示明确的空状态，不保留过期的手写更新内容。
- Mermaid 渲染失败：正文仍保留代码源，并在开发控制台报告错误；发布前必须修复首期范围页面中的渲染错误。
- 外部来源暂时不可访问：保留来源并标记检查结果，由人工判断是否更换；不因一次网络超时自动删除来源。

## 11. 测试与验收

### 11.1 自动检查

- 内容模型校验：必填字段、枚举、日期、路径和模块顺序。
- 内部链接检查：Markdown 链接、组件生成链接和导航路径。
- VitePress 生产构建。
- 草稿隔离检查：草稿不进入导航、搜索、最近更新和 sitemap。
- HTML 基础检查：canonical、Open Graph、Twitter Card、favicon 和 JSON-LD。

### 11.2 浏览器验收

至少在 360、768 和 1440 像素宽度检查：

- 首页知识地图和学习路径。
- 桌面三栏、平板双栏和手机单栏文章布局。
- 顶部导航、模块导航、文章目录和移动目录入口。
- 本地搜索和搜索结果跳转。
- 代码块、宽表格、图片和 Mermaid 图表。
- 浅色与深色模式。
- GitHub Pages `/notes-on-llms/` base 下的首页、二级页和深层文章直达。
- 浏览器控制台错误与明显布局偏移。

### 11.3 性能与可访问性

- 生产预览执行 Lighthouse 检查。
- 键盘可以访问主导航、搜索、目录和文章链接。
- 所有交互控件具有可识别名称和可见焦点。
- 颜色不能成为内容状态的唯一表达方式。
- 尊重 `prefers-reduced-motion`；首期不引入影响阅读的持续动画。

## 12. 发布顺序

首期实现按以下依赖顺序推进：

1. 建立内容模型、校验器和内容索引。
2. 修复 base 路径、favicon 和现有失效链接。
3. 拆分主题配置并建立页面组件。
4. 实现首页、学习路径、模块概览和文章页框架。
5. 完成首期入口内容重写与状态标记。
6. 补齐 SEO 和结构化数据。
7. 执行生产构建、自动检查、响应式验收和 Lighthouse 检查。

首期完成后，深层内容批次继续复用同一内容模型和组件，不再次改变站点架构。

## 13. 风险与控制

- **风险：AI 改写削弱作者声音。** 控制方式：保留原文观点和案例，逐篇 diff 审查，不进行无人审核的批量覆盖。
- **风险：当前技术事实仍可能快速变化。** 控制方式：记录核验日期和适用版本，优先引用官方与原始来源，定期将过期文章转为 `needs-review`。
- **风险：一次性范围过大。** 控制方式：首期只处理站点框架和入口内容，深层文章分六个批次推进。
- **风险：自定义主题影响 VitePress 升级。** 控制方式：通过标准主题扩展和小型组件实现，不复制或修改 VitePress 内部源码。
- **风险：构建检查过严阻塞正常写作。** 控制方式：正式文章执行严格校验，草稿允许本地编辑，但明确隔离于生产发布。

## 14. 最终决策

本次重构采用：

- VitePress 静态架构保留。
- “研究手册 + 知识地图”视觉方向。
- 统一文章内容模型和构建时内容索引。
- 构建阶段质量门禁。
- 首期完成站点框架和入口内容，深层技术文章按 RAG、Agent、MCP、Prompt、Training、Multimodal 顺序分批核验。

该方案在不增加运行时维护成本的前提下，解决当前路径可靠性、信息架构、内容可信度、视觉识别和后续维护问题。
